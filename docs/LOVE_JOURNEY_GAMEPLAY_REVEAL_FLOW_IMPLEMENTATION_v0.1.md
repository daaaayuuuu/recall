## 1. 本轮结论

本轮完成了以下调整：

1. 制作方试玩入口使用 `love-journey@1.1.0`，不再以旧模板配置验证新流程。
2. 场景 4 保留收拾 4 件行李的玩法；全部收好后，玩家需要向上滑动合上行李箱，随后完成本场景。
3. 场景 4 不再揭晓旅行照片，照片统一留到场景 5 展示。
4. 场景 5 使用创建者设置的 4 位拆信密码，不再对新版游戏使用固定密码。
5. 密码页打开 30 秒仍未解锁时，显示创建者填写的可选密码提示。
6. 密码正确后出现横向折叠信封；玩家每次上滑依次取出一张用户上传的照片。
7. 所有照片取出后，最后一次上滑取出并打开用户填写的情书；情书展示后才判定场景完成。
8. 场景 4 旅行箱已于 2026-08-21 接入蓝白手绘正式美术；场景 5 信封界面仍使用黑白线稿。旅行场景实施细节见 [LOVE_JOURNEY_TRAVEL_ART_IMPLEMENTATION_v0.1.md](./LOVE_JOURNEY_TRAVEL_ART_IMPLEMENTATION_v0.1.md)。
9. Worker 已能把加密资料中的情书、密码和提示写入可玩配置，并把用户照片复制为运行时素材。

## 2. 最终游玩流程

### 2.1 场景 4：旅行

旅行关卡包含相机、帽子、车票和充电器四件行李，状态机分为：

```text
packing -> ready-to-close -> closing -> completed
```

具体规则：

1. 玩家通过拖动或点击把 4 件物品放进行李箱。
2. 未收齐 4 件物品时，不能执行合箱操作。
3. 物品全部收好后，页面提示“向上滑动合上箱盖”。
4. 有效上滑、点击或键盘 Enter/Space 均可触发合箱动画。
5. 箱盖动画结束后，场景才发送完成事件。
6. 完成元数据记录 `packedItems = 4` 和 `suitcaseClosed = true`。
7. 本关不读取、不展示任何照片。

这样可以让旅行阶段保持完整的“收拾并出发”节奏，同时把真实素材集中到终局揭晓，避免照片在两个关卡重复出现。

### 2.2 场景 5：密码

新版游戏从运行时配置读取创建者设置的 `letterPassword`。密码固定为 4 位数字，玩家可转动页面上的四个数字轮并按下解锁，也可使用实体键盘输入。

数字轮在触摸端使用 38px 手势阈值，阈值内的轻微移动不翻页，同一次连续手势最多翻动一格；触控板或鼠标滚轮会累计到阈值后翻动一格，并在滚动停止后才允许下一次翻动。

密码错误时：

- 页面显示错误反馈并保留当前转轮数字，方便逐位调整；
- 不进入信封阶段；
- 玩家可以继续尝试。

密码正确时：

- 停止密码提示计时器；
- 隐藏已经显示的提示；
- 密码盒打开并展示盒内信封；
- 玩家点击信封后，密码盒退场，信封在页面中央展开；
- 展开的信封继续承载照片和情书抽取流程。

当前规则：新建和重置后的流程只以 `love-journey@1.1.0` 为验收目标，必须从生成配置取得有效的 4 位数字密码，不对缺失密码静默回退。代码中的 `1.0.0` 固定值只属于历史实现，不构成数据兼容承诺。

### 2.3 30 秒密码提示

当创建者填写了 `passwordHint` 时，密码页挂载后启动 30 秒计时：

- 只有密码关卡处于激活状态时才开始计时，提前挂载或停用期间不累计时间；
- 30 秒前不展示提示；
- 30 秒到达且密码尚未正确解开时，显示“提示：{创建者填写内容}”；
- 创建者未填写提示时，不创建提示计时器，也不展示空提示；
- 密码正确或组件卸载时清除计时器，避免进入信封阶段后再次出现提示。

### 2.4 照片与情书揭晓

密码正确后的状态机按以下顺序工作：

```text
密码盒打开 -> 点击盒内信封 -> 密码盒退场 / 信封展开
-> 照片 1 -> 照片 2 -> ... -> 最后一张照片 -> 情书 -> completed
```

每次有效上滑只取出一个内容项：

1. 先按运行时素材数组顺序依次取出全部照片。
2. 已取出的照片显示在信封上方，并标记“照片 1”“照片 2”等顺序。
3. 照片全部取出后，状态提示“再上滑一次打开情书”。
4. 最后一次上滑取出情书并显示完整正文。
5. 情书显示后才发送场景完成事件。

若用户没有上传任何照片，信封中的第一个内容项直接为情书，不会产生空白照片步骤。

## 3. 信封线稿调整

终局信封采用横向折叠结构，由 SVG 线条和 CSS 组成：

- 信封主体为横向矩形，而不是竖向袋状结构；
- 上方折页向后展开，形成可识别的三角开口；
- 待取出的照片或情书位于开口与信封前片之间；
- 滑出前只露出照片上方一角，让内容看起来确实放在信封内部；
- 信封前片使用不透明白色遮挡卡片下半部分；
- 照片卡片缩小并限制在信封左右边界内，避免穿出信封；
- 整体保持黑白线稿，以便后续替换为正式 UI 视觉稿。

当前交互同时支持手势、点击和键盘，方便桌面端调试并保留基础可访问性。

## 4. 生成与运行时素材链路

### 4.1 文字资料进入游戏配置

Worker 启动时初始化内容加密器。生成 `love-journey@1.1.0` 版本时执行以下过程：

1. 从 `game_versions` 读取加密的输入载荷、Nonce 和密钥版本。
2. 使用游戏版本 ID 作为附加认证数据解密载荷。
3. 从 `sceneInputs` 读取并去除首尾空白：
   - `loveLetter`
   - `letterPassword`
   - `passwordHint`
4. 将上述字段写入 `game-config` 产物。
5. 在写入对象存储前执行后端配置校验。

新版配置要求：

| 字段 | 是否必填 | 约束 |
|---|---:|---|
| `loveLetter` | 是 | 去除首尾空白后 1–1000 个 Unicode 字符 |
| `letterPassword` | 是 | 4 位数字 |
| `passwordHint` | 否 | 去除首尾空白后最多 100 个 Unicode 字符 |

Worker 因此必须配置有效的 `CONTENT_ENCRYPTION_KEY_V1` 和活动密钥版本；无法解密用户输入时，不能生成缺少密码或情书的伪成功产物。

### 4.2 用户照片进入运行时

生成阶段会读取当前游戏版本中可用的 `source` 和 `cover` 素材，逐张执行图生图，把模型结果重新解码并规范化为 PNG，再写入对象存储：

```text
game_source / game_cover
		-> ImageTransformer (/images/edits)
		-> PNG 解码、去元数据与校验
        -> gamegen-render-assets
        -> assets(kind = game_render)
        -> game_version_assets(role = render)
        -> 可玩接口签名 URL
        -> PasswordStage.photos
```

运行时素材使用生成 PNG 的 MIME 类型、校验和、尺寸，并保留源素材的槽位键和确定性展示顺序。数据库在生成成功事务中写入 `game_render` 素材记录及版本关联，随后才把游戏版本标记为 `ready`。

当前创建表单最多包含 1 张可选双人合照和 2 张可选旅行照片，因此新版游戏通常会在终局揭晓 0–3 张照片。运行时本身按素材数组处理，不把数量硬编码为 3。

### 4.3 失败清理

如果素材读取、图生图调用、生成图片校验、S3 写入或最终数据库事务失败，Worker 会清理已经写入的配置产物和运行时图片，避免对象存储残留孤立文件。取消任务或生成完成竞争时同样沿用现有清理逻辑。

## 5. 游戏配置契约变化

`contracts/game-config/v1.schema.json` 继续使用 `configVersion = 1`，但增加了 `love-journey@1.1.0` 所需字段：

```json
{
  "templateId": "love-journey",
  "templateVersion": "1.1.0",
  "configVersion": 1,
  "config": {
    "openingTitle": "我们的故事",
    "rounds": [],
    "loveLetter": "写给你的情书……",
    "letterPassword": "0123",
    "passwordHint": "我们的纪念日"
  }
}
```

其中 `loveLetter` 和 `letterPassword` 对 `love-journey@1.1.0` 必填，`passwordHint` 可选。前后端可玩配置类型、JSON Schema 与 OpenAPI 已同步这些字段。

1. 本轮没有新增数据库迁移，沿用现有 `assets` 和 `game_version_assets` 表结构。
2. 当前允许清空开发数据并从头创建，不提供旧版本恢复或迁移入口。
