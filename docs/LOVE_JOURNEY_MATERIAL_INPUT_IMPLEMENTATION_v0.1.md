## 1. 本轮结论

本轮已经将原有的“单段回忆文本 + 无明确用途的图片列表”改造成模板驱动的素材录入流程。

当前制作方可以：

1. 使用固定模板 `love-journey@1.0.0` 创建游戏草稿。
2. 按五个场景填写有独立长度和必填规则的文字。
3. 在游戏详情页按封面、初见、看电影和旅行等明确槽位上传图片。
4. 替换封面、初见和看电影等单图槽中的已有图片。
5. 为旅行场景上传恰好 3 张图片，并拖动调整揭晓顺序。
6. 基于当前文字创建新版本；新版本继承模板和文字，但从空素材槽开始。
7. 必填素材完整后提交约 3 分钟的占位生成任务，并继续验证制作方试玩、分享和公开游玩链路。

前端已接入五段可玩体验并保留原第 1–5 关编号；拼图不再作为独立体验，而是在初见、吃饭、看电影和旅行的主体玩法结束后依次以 5、4、3、2 块作为收尾，完成收尾拼图后才可进入下一幕，密码体验后不追加拼图。原流程末尾的第 6 关“擦除”已移除。第 1–5 关和四次收尾拼图均可实际游玩。Worker 已接入图生图并把生成 PNG 保存为版本专属 `game_render`；看电影与旅行仍需补齐按素材槽位消费这些正式图片的配置映射。

## 2. 模板与场景定义

### 2.1 模板身份

| 字段 | 值 |
|---|---|
| `templateId` | `love-journey` |
| `templateVersion` | `1.0.0` |
| `inputSchemaVersion` | `2` |
| `generationEnabled` | `true`（仅开发用占位生成器） |

模板注册表由后端维护，前端通过模板清单接口读取，不在页面中重复硬编码字段约束。

### 2.2 文字输入

| 场景 | 字段键 | 是否必填 | 最大长度 | 用途 |
|---|---|---:|---:|---|
| 初见 | `firstMeetingDescription` | 否 | 500 | 描述二人初遇的场景 |
| 吃饭 | `diningDescription` | 否 | 500 | 描述二人一起吃饭的回忆 |
| 看电影 | `movieDescription` | 否 | 500 | 描述第一次看电影的场景 |
| 旅行 | 无 | — | — | 本阶段只收集旅行照片 |
| 今天 | `loveLetter` | 是 | 1000 | 写给伴侣的最终情书 |

后端负责最终校验，包括未知字段拒绝、Unicode 字符长度判断和必填项检查。输入按版本加密后写入数据库，响应解密后以 `sceneInputs` 返回制作方。

### 2.3 图片素材槽

| 所属位置 | 槽位键 | 是否必传 | 数量 | 行为 |
|---|---|---:|---:|---|
| 封面 | `cover` | 否 | 0–1 | 再次上传时替换当前封面 |
| 初见 | `firstMeetingPartnerPhoto` | 是 | 1 | 再次上传时替换已有照片 |
| 看电影 | `moviePhoto` | 否 | 0–1 | 再次上传时替换已有照片 |
| 旅行 | `travelPhotos` | 是 | 3 | 最多 3 张，支持拖动排序 |

封面属于游戏级展示素材，但仍绑定到具体游戏版本的素材记录。当前封面视觉稿尚未完成，不影响用户上传入口和封面预览。

当前绑定策略是：素材所有权保留在上传时的版本中，`games.cover_asset_id` 指向最近一次选中的封面，用于游戏列表展示。创建新版本不会复制封面槽，也不会自动清除该游戏级展示指针；用户在任一可编辑版本上传或删除封面时会更新该指针。

## 3. 后端实现

### 3.1 模板注册表

新增 `backend/internal/gametemplates` 包，集中声明：

- 模板身份和输入 schema 版本；
- 五个场景的名称、说明和顺序；
- 文本字段的必填和长度约束；
- 图片槽位的最小数量、最大数量和是否可排序；
- 当前模板是否允许进入生成管线。

模板定义通过 `GET /api/v1/templates` 返回给已登录制作方。

### 3.2 加密输入 schema v2

新版本输入密文的逻辑结构为：

```json
{
  "sceneInputs": {
    "firstMeetingDescription": "……",
    "diningDescription": "……",
    "movieDescription": "……",
    "loveLetter": "……"
  }
}
```

数据库仍使用既有的密文、Nonce 和密钥版本字段，不把用户情书或场景描述明文写入关系型数据库。

旧的 `memoryText` 输入结构仍可由后端解密读取，避免已有旧版本在数据层立即失效。旧模板版本在当前新前端中只读展示兼容提示，不提供场景化新版本编辑。

### 3.3 游戏和版本绑定

创建游戏时必须提交模板 ID、模板版本和场景输入。服务端只接受注册表中存在的精确模板版本。

创建新版本时：

- 模板 ID 和模板版本从当前版本继承，客户端不能自行切换；
- 场景文字写入新的独立加密载荷；
- 新版本不会自动复制旧版本图片；
- 游戏的 `current_version_id` 指向新版本；
- 旧版本及其素材保持不变。

### 3.4 素材写入、替换与排序

图片上传请求新增 `slotKey`。服务端根据版本绑定的模板校验槽位，不信任客户端自行声明图片用途。

单图槽采用事务替换：

1. 锁定草稿版本。
2. 查询该槽位已有素材。
3. 删除旧素材关联及元数据。
4. 写入新素材和槽位关联。
5. 封面槽同步更新 `games.cover_asset_id`。
6. 数据库事务提交后清理已被替换的 MinIO 对象。

多图槽在同一版本锁下检查数量上限，避免并发上传突破模板声明的最大数量。

旅行照片排序使用独立接口。服务端要求提交的素材 ID 集合与该槽当前素材完全一致，拒绝重复、缺失或跨槽素材，然后按数组顺序更新 `sort_order`。

### 3.5 生成提交保护

生成提交增加模板素材完整性检查：

- 初见伴侣照片少于 1 张时拒绝提交；
- 旅行照片少于 3 张时拒绝提交；
- 必填素材完整后允许将 `love-journey` 提交给异步图生图 Worker；
- Worker 会产出图生图 PNG 和最小配置；配置仍未完成全部场景素材槽位映射，不得将其表述为完整正式配置。

## 4. 数据库迁移

新增迁移：

- `backend/db/migrations/000002_add_asset_slot_key.up.sql`
- `backend/db/migrations/000002_add_asset_slot_key.down.sql`

迁移向 `game_version_assets` 增加：

```sql
slot_key VARCHAR(64) NULL
```

并增加 `(game_version_id, slot_key, sort_order)` 索引。

`slot_key` 保持可空是为了兼容旧版本素材；新模板上传的素材必须具有有效槽位键。

本地开发数据库曾存在“旧邮箱账号 schema 已标记为迁移版本 1”的历史数据卷。经用户确认后，本轮已清空 development MySQL 和 MinIO 卷，从当前迁移文件重新建立数据库。最终状态：

- 迁移版本：`2`；
- `dirty=false`；
- `users.login_id` 存在；
- `game_version_assets.slot_key` 存在；
- 验证结束后账号、游戏和素材数量均为 0。

该清理仅作用于 `game-gen-dev` 本地开发环境，不涉及源码、配置文件或生产数据。

## 5. 接口变化

本轮实现使用的核心创建与版本输入已经同步到 OpenAPI；模板清单和素材排序接口仍待补充为完整契约。

### 5.1 模板清单

```http
GET /api/v1/templates
```

返回模板身份、输入 schema、封面槽、场景、文本输入和图片槽位定义。

### 5.2 创建游戏

```http
POST /api/v1/games
```

请求核心字段：

```json
{
  "title": "我们的故事",
  "description": "可选描述",
  "templateId": "love-journey",
  "templateVersion": "1.0.0",
  "sceneInputs": {
    "firstMeetingDescription": "……",
    "diningDescription": "……",
    "movieDescription": "……",
    "loveLetter": "……"
  }
}
```

### 5.3 创建版本

```http
POST /api/v1/games/{gameId}/versions
```

客户端只提交 `sceneInputs`。服务端从当前版本继承模板身份。

### 5.4 上传素材

```http
POST /api/v1/games/{gameId}/versions/{versionId}/assets
Content-Type: multipart/form-data
```

表单字段：

- `file`：单张 JPEG、PNG 或 WebP；
- `slotKey`：模板声明的素材槽位键；
- `sortOrder`：非负整数。

### 5.5 调整素材顺序

```http
PATCH /api/v1/games/{gameId}/versions/{versionId}/assets/order
```

请求示例：

```json
{
  "slotKey": "travelPhotos",
  "assetIds": ["asset-2", "asset-3", "asset-1"]
}
```

### 6.1 创建页

- 一封必填情书；

### 6.2 游戏详情页

详情页现在支持：

- 查看和编辑当前版本的场景文字；
- 以当前文字创建新版本；
- 分槽展示封面、初见、看电影和旅行图片；
- 单图槽“选择图片 / 替换图片”状态切换；
- 旅行槽上传到 3 张后禁用继续选择；

- 刷新后按服务端 `sort_order` 恢复顺序；
- 必填素材完整后开放“开始创建”，并展示排队、图生图和保存结果等真实状态。

## 11. 2026-08-17 前端游戏模板接入更新

后续实现已将独立示例合并进 `game-gen` 前端，并建立第一版受信任模板加载链路：

1. `love-journey@1.0.0` 通过前端注册表按 `templateId + templateVersion` 精确匹配并动态导入。
2. 模板内部固定采用原第 1 → 2 → 3 → 4 → 5 的五段线性流程；拼图不单独占用体验序号或公开路由，而是作为前四段主体玩法的收尾，完成后才可进入下一幕；原流程末尾的第 6 关“擦除”已移除。
3. 第 1 关“初见”、第 2 关“吃饭”、第 3 关“看电影”、第 4 关“旅行”和第 5 关“密码”均已迁入 Vue 模板并可实际游玩；前四关分别追加 5、4、3、2 块收尾拼图，密码体验后不追加拼图。
4. 每次拼图都在画面中上部提供带不规则虚线缺口的空白矩形，下部散落当前数量、具有互补凸榫与凹口的不规则拼图；鼠标或触摸拖入唯一匹配位置后吸附，全部放好即形成完整矩形并完成，同时提供聚焦后按 Enter/Space 的键盘替代操作。
5. 拼图块定位、正确槽位和完成判断已下沉到无模板视觉的纯 TypeScript 状态规则，页面布局和黑白线框视觉仍由 `love-journey` 模板负责。
6. 第 3 关通过三轮双方靠近完成看电影互动；第 4 关先将四件物品收入行李箱，再依次上滑或点击揭晓三张旅行照片。
7. 五段体验及其收尾拼图统一使用黑白线框视觉、方形操作控件、场景标识和底部状态反馈。
8. `memory-game@1.0.0` 继续使用历史占位组件，未知模板或未知精确版本会显示不支持提示，不自动回退到最新版。
