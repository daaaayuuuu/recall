# 个性化回忆游戏 MVP 整体技术选型

> 版本：v0.1
> 日期：2026-08-15
> 读者：产品、运营、设计及项目决策人员

> 具体模型候选、成本公式、缓存收益和评测方案见独立的 [AI 模型选型与成本测算](./AI_MODEL_SELECTION_v0.2.md)。


## 1. 一句话结论

MVP 采用“Vue 受信任模板 + 共用基础游戏引擎 + Go 业务服务 + 可替换图生图适配层”的方案：配置审核 Key 时，创建任务使用审核通过的用户图片生成个性化游戏图片；未配置时以明确的降级模式跳过审核。用户输入文本直接进入模板配置；不使用 AI 自动生成游戏文案，也不提供文生图。模型不生成程序代码，实际游戏始终由我们发布并审核的 Vue 模板运行。每套模板拥有独立页面和流程代码，可以组合拼图、翻牌等多个基础 2D 玩法。

## 2. 总体选型

| 部分 | MVP 选择 | 选择理由 |
| --- | --- | --- |
| 创作端、管理后台 | Vue 3 + TypeScript + Element Plus | 同一套前端技术覆盖注册登录、创建游戏、历史记录和后台管理，开发和维护成本较低。 |
| 分享后的游戏 | Vue 3 独立静态模板 + TypeScript 基础玩法引擎 | 模板负责完整页面与流程，拼图、翻牌等只复用规则和状态；无需引入 Unity、通用 3D 引擎或让 AI 生成网页代码。 |
| 后端 | Go 模块化单体服务 | 一套服务先承载用户、游戏、分享和管理功能，同时用独立后台任务处理耗时的 AI 生成，适合快速完成 MVP。 |
| 业务数据 | MySQL | 保存用户、游戏配置、任务结果、分享链接及错误记录。 |
| 图片存储 | 境内部署的 MinIO | 原图与生成图不写入数据库，通过临时授权地址访问，后续也便于迁移到境内对象存储。 |
| AI 平台 | 统一适配层，不预设供应商 | 上传审核、图生图和用户主动触发的文字润色彼此隔离，创建任务只依赖图生图。 |
| 文字模型 | 独立、可选 | 只用于用户主动点击的情书润色，不参与创建任务或模板文案自动生成。 |
| 图片模型 | 支持图片编辑的生产模型 | 只评测图生图，重点比较人物和参考图保真、画风、首轮通过率及每张合格图成本。 |
| 部署方式 | 中国大陆云服务器 + 容器化部署 | 应用、数据库、图片和模型调用均按境内服务设计，便于备案、运维和后续扩容。 |

## 3. 用户交互如何实现

创作者在网页选择模板、输入文本并上传参考图片。配置审核 Key 时，后端先用视觉 LLM 审核上传图；没有 Key 时记录并跳过。提交创建后，Worker 在配置图片模型 Key 时使用模板固定风格提示词执行图生图，否则复用源图；两种路径都会把输出规范化为 PNG 并保存到平台 S3。用户文本不经过自动扩写，直接按模板字段约束写入配置。前端展示排队、图片处理和保存结果等真实状态；任务完成后，后端产出经过校验的游戏配置和图片资源关联。

接收者打开有效分享链接后无需注册。页面按照游戏版本绑定的 `templateId + templateVersion` 从受信任注册表加载对应 Vue 模板，再把上述配置和临时图片地址填入模板。翻牌、拼图、点击、触摸、转场和轻量动画由浏览器直接完成，不依赖视频流或远程游戏服务。一局已经开始后最多可延续 30 分钟，分享链接最长有效 90 天。

## 4. 模型方案的判断

上传审核、图生图与可选文字润色分别选型，不要求来自同一家供应商。生产图生图只接入通过质量、合规、稳定性和有效成本门槛的模型；同一平台带来的账号、结算和监控便利，只在综合分接近时作为加分项。

模型通过后端统一的“模型适配层”调用，浏览器不直接接触模型密钥。业务代码不会绑定某个具体模型版本，未来可以在不修改游戏模板和基础玩法引擎的情况下更换供应商或开展效果对比。

正式确定图生图模型前，应使用经过授权的真实场景做小规模盲评，重点比较人物相似度、人数正确、失败率、生成时间和单局成本。评分权重和预算见 [AI 模型选型与成本测算](./AI_MODEL_SELECTION_v0.2.md)。

## 5. 安全、隐私与内容治理

- 只有配置图片模型 Key 时才向图生图供应商发送完成生成所必需的源图和模板固定风格提示词；模型返回的图片字节经过解码校验后保存到自有 MinIO/S3。未配置 Key 时图片不发送给该供应商，而是在本地规范化后保存。
- 上传原图、用户输入文本和生成图片均按私有内容管理；分享访问只获得该游戏版本允许公开的文本字段和短时有效的图片地址。
- 游戏模板仅接受预定义配置，模型不能输出或执行 HTML、JavaScript 等程序代码。
- 生成结果通过供应商内容安全机制和业务规则检查后才能进入可分享状态；被拒绝时向用户提供可理解的重试提示。
- 上线前需进一步确认所选云服务的用户数据留存、内容审核、个人信息处理条款，以及产品所需的备案与合规流程。
- 模型生成失败时记录阶段、错误类型和供应商请求编号，管理员可排查问题，但默认不查看用户原图、输入文本和生成文本素材正文。

## 6. MVP 阶段暂不引入

暂不引入微服务、Kubernetes、Redis、WebSocket、Unity、通用 3D/物理游戏引擎、多模型同时生产运行以及由 AI 动态生成游戏代码。基础 2D 玩法优先使用 Vue、DOM、CSS 和纯 TypeScript 状态引擎；只有某个玩法确实需要连续精灵动画或碰撞时，才在该引擎内评估轻量 2D 库。

## 7. 上线前仍需确认的产品参数

以下信息不影响先搭建整体框架，但会影响最终模型版本、生成时长和单局成本：

1. 每个游戏需要生成多少张图片，以及是否有统一画风。
2. 图片是否必须高度保留真人面部特征，还是允许明显的卡通化改编。
3. 用户可接受的最长生成等待时间和单个游戏的 AI 成本上限。
4. 每套模板需要哪些文本槽位、各槽位的长度与语气，以及生成后是否允许创作者修改。
